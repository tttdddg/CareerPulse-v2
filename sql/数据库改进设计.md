## 2. 表关系

```
job_clean (岗位实例，根表)
    job_id  ◄──────────── exemplar_job_id
                                │
                                │ 多个具体岗位按 normalized_job_title 聚合
                                ▼
job_type_profile (岗位类型)  type_key = 标准化岗位名（主键）
        ▲
        │ source_type_key / target_type_key
        │
job_type_graph_edge (类型间关系，有向边)

student_profile  ── 独立入口表，不与上述三表建立外键
```

**关系约束现状**：

| 关系                                                                  | 约束方式                        |
| ------------------------------------------------------------------- | --------------------------- |
| `job_type_profile.exemplar_job_id` → `job_clean.job_id`             | ✅ FK，`ON DELETE SET NULL`   |
| `job_type_graph_edge.source_type_key` → `job_type_profile.type_key` | ✅ FK，`ON DELETE RESTRICT`   |
| `job_type_graph_edge.target_type_key` → `job_type_profile.type_key` | ✅ FK，`ON DELETE RESTRICT`   |
| `job_clean.normalized_job_title` → `job_type_profile.type_key`      | ⚠️ **无 FK**，仅普通索引，靠灌数脚本保证一致 |

**「无 FK」的取舍说明**：插入顺序天然是「先有岗位实例，再聚合出类型」。若加 FK，灌数时就必须先建 `job_type_profile`，形成循环依赖。因此该关系由脚本保证，不在 DB 层强制。

## 4. 取值约定

### 4.1 `student_profile.parsed_data` JSON 结构

**9 个约定键**。前 6 个由 DB 强制校验，后 3 个为可选（存在时校验类型）。

```json
{
  "skills":            ["Python", "SQL/数据库", "后端开发"],
  "education":         {"degree": "本科", "major": "计算机科学与技术", "graduation_year": 2026},
  "target_job":        "初级后端开发工程师",
  "projects":          ["完成过一个课程管理系统 API，使用 Python 与 SQLite。"],
  "internships":       ["示例科技A 后端实习生（3个月）：参与内部管理系统接口联调。"],
  "certificates":      ["计算机等级考试"],

  "target_industry":   "互联网/软件服务",
  "city":              "上海",
  "supplementary_info": "目标是从初级后端岗位开始积累工程经验。"
}
```

| 键                    | 类型       | 必填    | 说明                                       |
| -------------------- | -------- | ----- | ---------------------------------------- |
| `skills`             | string[] | **是** | 统一能力标签，须来自标签字典                           |
| `education`          | object   | **是** | 含 `degree` / `major` / `graduation_year` |
| `target_job`         | string   | **是** | 建议对应 `job_type_profile.type_key`         |
| `projects`           | string[] | **是** | 见下方职责划分                                  |
| `internships`        | string[] | **是** | 见下方职责划分                                  |
| `certificates`       | string[] | **是** | 证书列表                                     |
| `target_industry`    | string   | 否     | 目标行业                                     |
| `city`               | string   | 否     | 期望城市，影响路径规划的地域适配评分                       |
| `supplementary_info` | string   | 否     | 补充说明                                     |

**`projects` 与 `internships` 的职责划分**：

| 字段            | 判定标准                           | 回答的问题       |
| ------------- | ------------------------------ | ----------- |
| `projects`    | **无组织归属**的自主产出（课程设计、个人项目、比赛作品） | 我自己做成了什么？   |
| `internships` | **有组织背景**的经历（公司/机构实习，存在雇主关系）   | 我在什么组织里做过事？ |

`internships` 书写约定：`组织 职位（时长）：做了什么`。

**不写入本字段的内容**：姓名、电话、邮箱、身份证等身份信息；以及匹配分数、竞争力得分等 Agent 计算输出（这些属于计算产物，不是事实证据）。

**结构统一要求**：`skills` / `projects` / `internships` / `certificates` **一律为字符串数组**，`education` **一律为对象**。禁止出现「同一字段有时是字符串、有时是数组」的情况，该要求由 CHECK 约束强制。

### 4.2 `level_range` 五级取值

`entry` / `junior` / `mid` / `senior` / `lead`

### 4.3 `relation_type` 取值

| 值          | 含义   |
| ---------- | ---- |
| `vertical` | 晋升   |
| `lateral`  | 横向换岗 |

**只允许英文枚举**。历史数据中的 `晋升` / `平移` / `promotion` / `career_change` 等混用形式不得进入本库。

### 4.4 `risk_level` 取值

`low` / `medium` / `high`

### 4.4.1 `salary_range` 文本约定

统一格式为 **`A-B（单位）`** 或 **`A（单位）`**，`A-B` 为数值区间，单位置于全角括号内。

| 单位                          | 适用场景                | 示例                   |
| --------------------------- | ------------------- | -------------------- |
| `K`                         | 月薪 ≥ 1000 元，一律折算为 K | `8-15（K）`、`20-40（K）` |
| `K·13薪` / `K·14薪` / `K·24薪` | 带薪数                 | `6-10（K·13薪）`        |
| `元`                         | 月薪 < 1000 元         | `800（元）`             |
| `元/天`                       | 日薪                  | `100-150（元/天）`       |
| `面议`                        | 无具体数字               | `面议`（保持不变，不作换算）      |

**换算规则**：原数据中的 `1.5-3万`、`8000-15000元` 量级相同，一律折算为 K；`万` 按 ×10 折 K（1 万 = 10K），`元` 按 ÷1000 折 K。带薪数的描述保留。

**禁止**的写法：`1.5-3万`、`8000-15000元`、`5000-8000元·13薪`（单位与数值混排、无括号分隔）。

### 4.4.2 `job_description` 内容边界

`job_description` **只存放岗位要求相关内容**（岗位职责、任职要求、加分项、技能要求等）。

**不得出现**：

| 内容                              | 处理方式                  |
| ------------------------------- | --------------------- |
| 公司简介段落（独立成段、有"公司简介/我司简介/名片"等标记） | **整段删除**              |
| 通篇公司宣传段落（无岗位信息价值）               | **整段删除**              |
| 公司全名嵌入正文句子中                     | 用 `***` 替换公司全名，保留句子结构 |
| 邮箱、手机号、微信号、QQ 号                 | 删除该行或替换为脱敏占位符         |
| 低俗、不当表述                         | 删除该句                  |

判定原则：**短的小句子直接删除；删掉会破坏句子完整性的，用 `***` 替换全名**。

### 4.4.3 `industry` 行业字段约定

**语义**：`job_clean.industry` 记录的是**岗位所属行业**（脱离公司），不是公司所处行业。

因此同一批数据里，同一岗位类型下的行业**大体相同**；若某条岗位的 JD 额外涉及其他领域，可如实补充。

**格式**：细粒度，多行业用 `/` 分隔。示例：

```
互联网/计算机软件/数据服务
医疗设备/器械/机器人/人工智能
政务/智慧城市/IT服务
```

**判定依据**：逐条阅读 `job_description` 的业务场景，判断该岗位实际服务于什么行业。

**聚合规则（对 `job_type_profile.industry`）**：按**通识知识归为大体行业**，去掉个别岗位补充的边角行业，取该类型的主导行业。

判定示例：

| 类型       | `job_clean` 逐行判定                                     | `job_type_profile` 聚合（通识主导） |
| -------- | ---------------------------------------------------- | --------------------------- |
| 3D建模师    | ①互联网/计算机软件/数据服务<br>②测绘/地理信息/建筑设计<br>③游戏/影视动画/数字媒体    | 游戏/影视动画/数字媒体                |
| 嵌入式开发工程师 | ①工业自动化/物联网/电子制造<br>②嵌入式/电子/物联网<br>③智能硬件/物联网/消费电子     | 嵌入式/电子/物联网                  |
| 数据分析师    | ①电子商务/私域运营/健康消费<br>②农副产品/贸易/大宗商品/金融<br>③政务/智慧城市/IT服务 | 互联网/数据服务                    |

> 逐行保留行业差异的意义：`job_clean` 是岗位实例，如实记录该岗位的真实业务领域；
> `job_type_profile` 是类型画像，需要稳定的代表性行业，故去除边角。

### 4.4.4 `job_description` 空格约定

**目的**：JD 文本用于喂给 Agent，越紧凑越利于传输与解析。

**规则**：

| 处理     | 内容                                                       |
| ------ | -------------------------------------------------------- |
| **保留** | 英文单词之间的空格（`Latin                                         |
| **删除** | 中文与中文之间的空格                                               |
| **删除** | 中文与英文/数字之间的空格                                            |
| **删除** | 中英文标点前后的空格                                               |
| **删除** | 行首、行尾空格，多余空行                                             |
| **删除** | 不可见字符（零宽空格 `\u200b`、`\u200c`、`\ufeff` 及私用区符号 `\uf0d8` 等） |

**效果示例**：

```
改前：岗位职责： 1、按产品需求规格说明书，进行软件功能模块的开发...
改后：岗位职责：1、按产品需求规格说明书，进行软件功能模块的开发...
```

**例外说明**：英文标点后的空格也一并删除（如 `Reporting to: Service` → `Reporting to:Service`），
原因是 LLM 对标点粘连的英文仍可正确切词，而删除后文本更紧凑。

### 4.5 `transfer_cost` / `growth_value` 定档规则

这两个字段是路径评分的直接输入，不能随意取值，须按下列档位填写。

**在评分公式中的位置**：

```
growth   = Σ edge.growth_value      # 路径上所有边累加
transfer = Σ edge.transfer_cost     # 路径上所有边累加
base     = growth - transfer - gap_cost
time_months = Σ 节点停留月数 + transfer × 6.0
```

`growth_value` 与路径得分正相关，`transfer_cost` 与路径得分负相关，且 `transfer_cost` 是唯二影响时间估算的因子（每 1.0 折合 6 个月）。

**取值锚点**：下表档位由 `backend/app/data/career_graph.json` 中 16 条已设计边的实际取值归纳而来，可作为新边的填写依据。

#### `transfer_cost`（转移成本）

| 判定条件                                 | 取值        |
| ------------------------------------ | --------- |
| 同行业 · 相邻层级晋升（跨度 1）· 起点为 entry/junior | 0.6 ~ 0.8 |
| 同行业 · 相邻层级晋升（跨度 1）· 起点为 mid 及以上      | 1.4 ~ 1.5 |
| 跨行业 · 职能相近                           | 0.8 ~ 1.0 |
| 跨行业 · 跨职能                            | 1.2 ~ 1.5 |
| 跨行业 · 跨职能 · 起点层级高或职能差异大              | 1.6 ~ 1.8 |
| 任意 · 层级跨度 ≥ 3                        | 2.0 ~ 2.2 |

**规律**：成本由「**起点层级**」与「**跨度**」共同决定。同样的跨度 1，起点为 entry 时取 0.6~0.8，起点为 mid 时取 1.4~1.5 —— 层级越高，晋升成本越大。同时「跨行业 + 跨职能」会显著抬升成本。

#### `growth_value`（成长价值）

| 判定条件                  | 取值        |
| --------------------- | --------- |
| 跨度 0（平级换岗）            | 1.3 ~ 1.6 |
| 跨度 −1（降级换岗）           | 1.7 ~ 2.1 |
| 跨度 +1 晋升              | 1.8 ~ 2.2 |
| 跨度 +1 晋升（起点为 mid 及以上） | 2.4 ~ 2.8 |
| 跨度 +2 晋升              | 2.2 ~ 2.4 |
| 跨度 +3 晋升              | 3.0       |

**规律**：成长价值主要由「**层级跨度**」决定，跨度越大成长越高；相同跨度下，晋升高于平级换岗。

#### `risk_level`（风险）

| 判定条件                         | 取值       |
| ---------------------------- | -------- |
| 同行业 · 跨度 1 的 vertical        | `low`    |
| 任意跨行业的 lateral               | `high`   |
| 跨度 ≥ 3 的 vertical            | `high`   |
| 其余（同行业跨度 ≥ 2 的晋升、跨度 0 的横向换岗） | `medium` |

**注意**：`risk_level` **不由 `transfer_cost` 派生**。实测数据中存在反例——`ai-product-assistant → data-analyst` 的 `transfer_cost` 仅 1.3 但 `risk_level` 为 `high`；而 `ai-product-manager → senior-ai-product-manager` 的 `transfer_cost` 达 1.5 却为 `medium`。风险等级取决于「**是否跨行业**」「**是否换职能**」「**跨度大小**」，与成本是两个独立维度。

**三者需保持自洽**：同一条边的三个值应能同时被上表解释；若出现矛盾（如跨行业 lateral 却标 `low`），应在灌数脚本中报错。

### 4.7 岗位类型画像聚合口径

`job_type_profile` 各字段由 `job_clean` 按 `normalized_job_title` 聚合而来。

**总原则**：画像以**该岗位在招聘市场上的普遍水平**为基准（模型通识认知为主），JD 内容用于校验与补充细节，**不做机械词频统计**。

| 字段                | 聚合口径                                                                                                                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type_key`        | 等于 `normalized_job_title`，不含行业/城市/公司                                                                                                                                                                                                          |
| `industry`        | 按通识取该类型**主导行业**，去除个别岗位的边角行业（规则见 §4.4.3）                                                                                                                                                                                                       |
| `sample_size`     | 该类型在 `job_clean` 中的行数（2 或 3）                                                                                                                                                                                                                  |
| `core_skills`     | 该类型普遍要求的核心技能，取自 §4.6 词表                                                                                                                                                                                                                       |
| `optional_skills` | 加分项类技能                                                                                                                                                                                                                                        |
| `soft_skills`     | 软技能，取自 §4.6 词表的 `soft_skill` 类                                                                                                                                                                                                                |
| `salary_desc_p50` | 该类型薪资的中位描述，**统一为纯月薪形式 `A-B（K）`**（小数保留）。计算分两层：**①样本筛选**——仅「月薪类」（单位为 `K`，含带薪数形式）样本参与中位计算，`面议` 与日薪（`元/天`）**不参与**；**②取中位**——3 条及以上取数值排序中间者，2 条取偏低者，1 条取该条。**兜底**：若该类型全部样本均为日薪（无月薪样本），则按 **日薪 × 30 天**折算为月薪后取中位。**不带薪数**：`K·13薪` 等后缀属具体岗位信息，不写入画像。 |
| `exemplar_job_id` | 取该类型下**最具代表性**（JD 最完整、最贴合普遍要求）的一条，FK → `job_clean.job_id`                                                                                                                                                                                     |
| `profile_summary` | 该类型画像摘要，一段 80~150 字，覆盖「做什么 / 要什么能力 / 适合谁 / 发展走向」，展示层用它覆盖 `job_description`                                                                                                                                                                    |

**设计口径**：

| 项                         | 约定                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------- |
| `relation_type` 判定        | 目标层级**更高** → `vertical`；**同层级** → `lateral`                                                    |

| `高级X` 三个节点                | 为职业终点，出度为 0，只作晋升目标                                                                             |
| 定档依据                      | `transfer_cost` / `growth_value` / `risk_level` 的档位规则见 §4.5                                    |
| `transition_requirements` | 取自 §4.6 技能词表                                                                                   |

## 6. CHECK 约束的能力边界

**CHECK 校验「结构与类型」，不校验「语义与内容」。**

| CHECK 能保证            | CHECK 无法保证                    |
| -------------------- | ----------------------------- |
| `skills` 是数组         | 数组里的标签是否合法                    |
| `education` 是对象      | 专业、学历是否合理                     |
| `target_job` 存在且为字符串 | 该岗位是否真实存在于 `job_type_profile` |
| 技能元素是字符串             | 是否为标签字典中的标准标签                 |

**原因**：CHECK 表达式只能使用常量，不能读取外部文件（标签字典在 `ability_tags.json`），不推荐跨表查询。

**因此校验分层**：

```
DB 层 CHECK      →  结构（类型对不对、必填键在不在）
代码层 Service   →  语义（标签是否在字典内、数据是否可用）
```
