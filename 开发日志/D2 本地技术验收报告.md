## 六、P1 问题

### 【P1-1】ProfileAgent 和 JobAgent 的 `run()` 覆写模式重复
【严重程度：P1】
【文件】`profile_agent.py:45-58`、`job_agent.py:63-76`
【原因】两个 Agent 各自复制了完全相同的 `run()` 覆写（调用 `super().run()` → 根据 status 替换 summary → 后补 `state.agent_logs[-1].summary`）。复习上一次审查的问题1，该模式未被修复就复制到了 JobAgent。如果继续，6 个 Agent 将各自有一份重复代码。
【建议】阶段3 开始前在 BaseAgent 中增加 `_summary_for_status()` 模板方法，两个 Agent 删除 `run()` 覆写。

### 【P1-2】JobAgent 零专项测试
【严重程度：P1】
【文件】缺失 `backend/app/agents/tests/test_job_agent.py`
【原因】ProfileAgent 有 7 个测试（LLM 成功/重试/fallback/隐私/注入），JobAgent 没有。JobAgent 的 grounding validation（`_validate_grounding`）是整个阶段2中最复杂的校验逻辑——JD evidence 强制检验、趋势技能强制检验、无趋势上下文强制保守——没有测试覆盖就直接依赖。
【建议】阶段3前补写至少 6 个 JobAgent 测试：
- `test_jd_provided_generates_grounded_profile` — 正常 JD → evidence 来自 JD
- `test_no_jd_enters_fallback` — 无 JD → rule tags + Demo
- `test_no_trend_context_produces_conservative_output` — 无趋势 → 全部空+medium占位
- `test_trend_context_isolated_from_jd_requirements` — 趋势技能不入 required_abilities
- `test_retry_twice_then_fallback` — 3次LLM失败 → fallback
- `test_logs_exclude_pii` — 隐私脱敏

## 七、P2 问题

### 【P2-1】`_TAG_ALIASES` 与 `AbilityTagNormalizer` 存在两套别名系统
【严重程度：P2】
【文件】`job_agent.py:33-42` vs `services/ability_normalization.py` + `data/ability_tag_aliases.json`
【原因】JobAgent 硬编码了 8 个别名在 `_TAG_ALIASES` 中（如 `"JavaScript"→"JavaScript/TypeScript"`），而正式的别名管理系统在 `ability_tag_aliases.json`（44 条，含 "JavaScript"→"JavaScript/TypeScript"）。当在 `ability_tag_aliases.json` 中新增别名时，JobAgent 的 `_rule_tags()` 不会自动感知。
【建议】JobAgent 的 `_rule_tags()` 改用 `AbilityTagNormalizer` 的 `normalize()` 方法（与 MatchService 保持一致）。这是非阻塞问题——当前 8 个硬编码别名在 `ability_tag_aliases.json` 中也存在，不冲突。

### 【P2-2】MatchService 与 MatchAgent `_calculate()` 存在两套匹配逻辑
【严重程度：P2】
【文件】`services/match_service.py` vs `agents/match_agent.py:24-86`
【原因】成员2 在阶段2实现了 `MatchService`（带 `AbilityTagNormalizer`、`_WEIGHT_TOLERANCE`），但 `match_agent.py` 的 `_calculate()` 方法仍用自己的版本（未调用 MatchService）。Orchestrator 目前走的是 match_agent.py 的旧实现。两套逻辑在公式上一致，但 MatchService 增加了归一化和更严格的校验。**这属于"提前准备"而非冲突——阶段3 设计本就是 MatchAgent 接入 MatchService**。

### 【P2-3】`agent_logs` 中 `demo` 字段未填充
【严重程度：P2】
【文件】`base_agent.py:92-98`
【原因】`AgentLog` 含 `demo` 字段（`06_DATA_DICTIONARY.md` 定义的 agent_logs 表 `demo BOOLEAN NOT NULL DEFAULT false`），但 `BaseAgent.run()` 创建 `AgentLog` 时通过 `**result.model_dump(exclude={"data"})` 传入字段，而 `AgentResult` 无 `demo` 字段。因此 `demo` 字段始终为 `False`（Pydantic 默认），Demo Mode 的日志不会区分。
【建议】在 `AgentResult` 中增加 `demo: bool = False` 字段，ProfileAgent/JobAgent 在 Demo 模式时设置。

### 【P2-4】`schemas/common.py` 未创建
【严重程度：P2】
【文件】`backend/app/schemas/common.py`（不存在）
【原因】D2 架构文档约定但未创建。当前未使用（Agent 和工具用各自的 Schema），但统一错误格式和工具响应 Pydantic 模型在阶段5（MCP/API正式接入）前必须到位。
